# OmniStore — First Company GO-LIVE

This guide takes a clean Windows machine from zero to a running OmniStore
company: install, provision the first company + admin, log in, operate, back
up, and update — without ever touching company data during upgrades.

> The desktop application is the OmniStore PWA (single-file frontend +
> Node backend). "Install the app" means: install the backend (option A/B
> below), open `http://localhost:3001` in a browser, and use the browser's
> **Install app** option to get the standalone desktop window.

---

## 1. Prerequisites

| Requirement | Value |
|---|---|
| OS | Windows 10/11 64-bit (server-class recommended) |
| Node.js | **18+** (LTS recommended) — `node -v` must succeed |
| Disk | ≥ 500 MB free (release + data) |
| Port | 3001 free (configurable via `PORT`) |
| Browser | Chrome/Edge (for the PWA install) |

Check:

```powershell
node -v        # e.g. v20.x
npm -v
```

## 2. Environment Variables

All configuration lives in `.env` next to the app root (generated by the
installer; `dotenv` loads it at startup). Required in production:

| Variable | Purpose | Required |
|---|---|---|
| `JWT_SECRET` | Access-token signing (random 48-byte base64) | YES |
| `JWT_REFRESH_SECRET` | Refresh-token signing | YES |
| `AUTH_REQUIRED` | `true` — protect all business routes | YES |
| `DIGITRONICS_DATA_DIR` | **Company data directory — outside the app dir** | YES |
| `PORT` | HTTP port (default 3001) | no |
| `UPDATE_ENABLED` | In-app update rail (default true) | no |
| `UPDATE_MANIFEST_PATH` | Path to `updateManifest.json` | no |
| `UPDATE_STOP_COMMAND` / `UPDATE_START_COMMAND` | Service stop/start for updates (e.g. `net stop/start OmniStoreBackend`) | no |
| `CORS_ORIGINS` | Allowed browser origins (LAN clients) | no |

Never commit `.env`. The installer generates random secrets.

## 3. Database / Data Directory Requirements

- **Persistence today is JSON file storage** (PostgreSQL arrives in a later
  phase). The data directory is `DIGITRONICS_DATA_DIR` (default
  `backend/data`).
- **The data directory must live OUTSIDE the application directory** (e.g.
  `C:\OmniStore\data`). The updater refuses to run if data is inside the app
  dir — company data is never part of an update package and is never deleted.
- Back up the data directory (see §7). It is the single source of truth.

## 4. First Company Creation

Option A — Windows installer (recommended for a clean machine):

```powershell
# from a machine with the release zip + this repo (or a tools copy):
powershell -ExecutionPolicy Bypass -File scripts\install-windows.ps1 `
  -ZipPath .\releases\OmniStore-1.0.0.zip -InstallDir C:\OmniStore -Port 3001
```

Option B — manual (dev / existing checkout):

```bash
npm install          # installs backend deps
npm start            # or: npm run dev
```

Then provision the first company (idempotent — safe to re-run):

```bash
npm run provision -- --company-name "Acme Trading" --company-code ACME \
  --admin-username admin --admin-password '<strong-password>' --admin-role Owner
```

Or via environment variables: `COMPANY_NAME`, `COMPANY_CODE`, `COMPANY_ID`,
`ADMIN_USERNAME`, `ADMIN_PASSWORD`, `ADMIN_ROLE`.

## 5. First Admin Creation

The provisioning command above **creates the admin user and the company
together**, with a company-scoped membership:

- user `admin` (bcrypt-hashed password — never printed, never logged)
- membership: `tenantIds: ["acme"]`, `tenantRoles: { "acme": "Owner" }`
- company record: `{ id: "acme", code: "ACME", name: "Acme Trading", active: true }`

Re-running the command never changes the password and never duplicates the
company or the user (it only ensures membership).

## 6. Login

1. Open `http://localhost:3001`.
2. At company selection choose **Acme Trading** (from `GET /api/v1/companies/active`).
3. Log in as `admin` with the password chosen at provisioning.
4. Verify: `GET /api/v1/auth/me` returns your user; the tenant context
   (`corp`) is carried in the JWT and enforced on every request.

Company data is tenant-scoped: customers, sales, purchases, treasury. Products
(and apiKeys/errors/jobs/webhooks) are global.

## 7. Backup

The data directory is the single source of truth — back it up:

```bash
npm run backup           # backend/scripts/backup.js — zips the data dir
npm run verify-backup    # backend/scripts/verify.js — integrity check
```

Restore:

```bash
npm run restore          # backend/scripts/restore.js
```

Automatic update backups: every in-app update keeps the previous application
version under `backups/` (see §8).

## 8. Update Procedure

The application contains a built-in **update rail** (Arabic-first, non-
blocking):

1. The PWA periodically calls `GET /api/v1/update/manifest`.
2. If a newer version exists it shows: *يوجد تحديث جديد لـ OmniStore* with
   current/latest version, release notes, and **[تحديث الآن]** / **[لاحقًا]**.
3. **[تحديث الآن]** calls `POST /api/v1/update/apply` (admin-gated). A
   **separate updater process** (`backend/scripts/update/apply-update.js`)
   runs detached:
   1. downloads the release archive (HTTPS)
   2. verifies SHA-256 against the manifest
   3. verifies version metadata
   4. **backs up** the current installation (`<app>.previous-<version>`)
   5. stops the service (`UPDATE_STOP_COMMAND`)
   6. swaps the new version into place atomically
   7. starts the service (`UPDATE_START_COMMAND`)
   8. health-checks `GET /api/v1/health`
   9. on failure → **rolls back** automatically
4. Company data (`DIGITRONICS_DATA_DIR`) is never touched.

Publish a new release:

```bash
npm run build:release                     # builds releases/OmniStore-<v>.zip
npm run update:manifest -- --release-zip "releases/OmniStore-<v>.zip" \
  --download-url "https://<host>/OmniStore-<v>.zip" \
  --version <v> --release-notes "..." [--mandatory]
```

The manifest is written to `backend/data/updateManifest.json`
(`UPDATE_MANIFEST_PATH`). Client check interval: `UPDATE_CHECK_INTERVAL_MS`
(default 6 h) or the `eso_update_check_interval` localStorage key.

## 9. Rollback Procedure

- **Automatic:** the updater rolls back if the new version fails its health
  check (previous install is preserved as `<app>.previous-<version>` and
  restored automatically).
- **Manual:** restore the latest previous-version backup:
  - stop the service (`net stop OmniStoreBackend`),
  - replace the app directory from `backups/` (or re-run the installer with
    the previous release zip),
  - start the service, verify `GET /api/v1/health`.
- **Data:** never roll back by deleting/replacing `DIGITRONICS_DATA_DIR` —
  that directory is version-independent.

## 10. Verification Checklist

- [ ] `node -v` ≥ 18 and backend starts without errors
- [ ] `GET /api/v1/health` → `{ status: "ok" }`
- [ ] `npm run provision` created exactly one company + one admin
- [ ] Admin can log in with company selection (multi-company login works)
- [ ] Create a product (global) → visible; create customer/sale/purchase/
      treasury (tenant-scoped)
- [ ] Tenant isolation: a second company cannot read the first company's data
- [ ] Restart the backend → data persists
- [ ] `npm run backup` produces a verifiable archive
- [ ] Update manifest endpoint returns the current version
- [ ] Publish a newer release → banner appears in the PWA with Arabic text
- [ ] Update applies, SHA-256 verified, previous version kept, new version
      starts healthy
- [ ] AUTH_REQUIRED=true and strong random JWT secrets in `.env`
- [ ] Data dir is outside the app dir (updater safety invariant)
